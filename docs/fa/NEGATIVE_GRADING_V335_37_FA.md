# V335.37 — نمرهٔ منفی، تصحیح و کارنامه — اپ 1.03.18

## سیاست تأییدشدهٔ کاربر

جریمهٔ سؤال‌های چندگزینه‌ای و صحیح/غلط برابر «ضریب منفی آزمون × بارم سؤال» است. پاسخ درست بارم کامل، پاسخ بی‌پاسخ صفر، و پاسخ غلط مشمول جریمه نمرهٔ منفی دارد. سؤال تشریحی، عددی، جای‌خالی، جورکردنی و زیربخش‌ها مطابق قواعد قبلی‌اند؛ اجازهٔ منفی نامحدود به همهٔ سؤال‌ها داده نشده است.

نمرهٔ کل = `max(0, sum(grades))`. خود آرایهٔ نمره‌ها منفی می‌ماند. نصب SQL به‌تنهایی هیچ پاسخ یا نمرهٔ تاریخی را تغییر نمی‌دهد و بازتصحیح همگانی انجام نمی‌دهد.

## محتوا

- قاعدهٔ مشترک SQL برای ثبت پاسخ، تأیید خودکار و نهایی‌سازی؛ حفظ نمرهٔ دستی نهایی‌شده و پیشرفتِ تصحیح دستی.
- ذخیرهٔ فردی و گروهی با کف متناسبِ سؤال و ضریب؛ رد مقدار null/گمشده/غیرعددی؛ اعتبارسنجی زیربخش‌ها.
- نهایی‌سازی همه‌یا‌هیچ: اگر سؤال دستی نمره ندارد، هیچ برگه یا رکورد پیشرفتی تغییر نمی‌کند.
- رعایت `shown_q` در بازتصحیح؛ جلوگیری از تزریق متادیتای انتخاب سؤال از کلاینت در ثبت جدید.
- هماهنگی اپ و سایت، جلوگیری از خطای Promise بی‌پاسخ در اعتبارسنجی سایت، و نمایش برچسب درصد منفی در تحلیل؛ فقط عرض میلهٔ نمودار محدود می‌شود.
- سؤال چندبخشی باید در تصحیح فردی ذخیره شود تا نمره و بازخورد زیربخش‌ها از بین نروند.

## انتشار ایمن در دو مرحله

این نسخه به انتخاب صریح کاربر **فقط اصلاح تصحیح** را منتشر می‌کند. تغییرات محلی پل ایرانی، اطلس، ظاهر گوشی و سایر کارهای ذخیره‌نشده، در پوشهٔ اصلی محفوظ می‌مانند و وارد این انتشار نمی‌شوند.

نصاب مستقل tar.gz/base64 است. در کنار پوشهٔ اصلی، پوشهٔ `exam-app-kotlin-grading-v335-37` را با `git worktree` از پایهٔ منتشرشدهٔ `69e9af22...` می‌سازد. فایل‌ها فقط در این پوشهٔ جدا استخراج و بررسی می‌شوند؛ تنها فایل‌های بسته در همان پوشه commit و فقط به ریموت staging ارسال می‌شوند. پوشهٔ اصلی checkout، clean، reset، stash، stage یا commit نمی‌شود. شاخهٔ main محلیِ اصلی و تغییرات stage/unstaged و untracked آن دست‌نخورده می‌مانند. یک شاخهٔ پشتیبان فقط برای HEAD قبلی نیز ساخته می‌شود؛ این شاخه پشتیبان محتوای ذخیره‌نشده نیست، چون آن محتوا اصلاً جابه‌جا نمی‌شود.

نصاب وضعیت و اثرانگشت تغییرهای پوشهٔ اصلی را قبل/بعد مقایسه می‌کند. رسید مسیر پوشهٔ جدا، در متادیتای Git با نام `onlineexam-v335-37-isolated.json` ثبت می‌شود؛ حاوی رمز نیست. پوشهٔ جدا و رسید را تا پایان ارتقا جابه‌جا یا حذف نکنید. هیچ git apply، force-push یا بازنویسی فایل شخصی وجود ندارد. تغییر مستقل ریموت‌ها یا تغییر ناشناخته در پوشهٔ انتشار، باعث توقف ایمن می‌شود.

نیازمندی: Python 3، Git با پشتیبانی worktree، Node.js 20+، npm و فضای کافی برای یک worktree دیگر. PGlite 0.5.12 در کش بیرون مخزن نصب می‌شود و فقط پایگاه دادهٔ حافظه‌ای ساختگی دارد. خود نصاب به Supabase متصل نمی‌شود. در پوشهٔ اصلی می‌توانید همان تغییرات فعلی را داشته باشید؛ دیگر لازم نیست برای نصب این بسته آن‌ها را حذف یا کامیت کنید. هنگام اجرای نصاب بهتر است فایل‌های اصلی را هم‌زمان ویرایش نکنید.

### ۲) SQL جداگانه — خودکار اجرا نمی‌شود

**staging و main فعلاً Supabase مشترک دارند. انتشار staging، آزمایش دیتابیس را از production جدا نمی‌کند. اجرای SQL روی همین پروژه، توابع سرورِ هر دو نسخه را فوراً تغییر می‌دهد. ابتدا روی دیتابیس مجزا/کپی آزمایشی اجرا کنید.**

در SQL Editor دیتابیس مقصد مجاز:

1. `sql/manual/SQL_NEGATIVE_GRADING_V335_37_CHECK.sql` را اجرا و نسخهٔ توابع/قیود/تریگرها را بررسی کنید؛ این فایل فقط خواندنی است.
2. `sql/manual/SQL_NEGATIVE_GRADING_V335_37_BACKUP.sql` را اجرا و خروجی کامل را خصوصی ذخیره کنید؛ شامل تعریف تابع و متادیتای ACL/مالک برای بازگشت است. نسخهٔ پشتیبان خود دیتابیس نیز توصیه می‌شود.
3. فایل `sql/manual/SQL_NEGATIVE_GRADING_V335_37.sql` را کامل اجرا کنید. این همان `supabase/migrations/20261027_native_negative_grading_v335_37.sql` است؛ لازم نیست هر دو را اجرا کنید. در مخزن، هر دو فایل داخل پوشهٔ جداگانهٔ انتشار هستند، نه پوشهٔ اصلی دست‌نخورده.
4. مهاجرت، اثرانگشت هفت تابع قبلی را با نسخه‌های بررسی‌شده تطبیق می‌دهد؛ هم پایهٔ اصلی و هم تعریف‌های SQL ارسالی و اجراشدهٔ V335.36 پذیرفته می‌شوند. نیازی به بازگردانی یا اجرای دوبارهٔ SQL قدیمی V335.35 نیست. اگر پیام `V335.37 safety stop` داد، هیچ تغییری از این تراکنش اعمال نمی‌شود. guard را حذف نکنید و به‌زور ادامه ندهید؛ نسخهٔ نصب‌شده متفاوت است و باید بررسی شود. اجرای مجدد همان مهاجرتِ موفق مجاز است.
5. SQL تاریخچهٔ نمره و پاسخ را دست نمی‌زند. اصلاح نمره‌های اشتباه قبلی فقط با پیش‌نمایش، پشتیبان و انتخاب مشخص معلم انجام شود؛ این بسته ترمیم انبوه ندارد.

اگر لازم شد به نسخهٔ توابع قبلی برگردید، تعاریف و ACLهای ذخیره‌شده را با مالک مجاز بازیابی کنید. این بازگشت، تغییر نمره‌ای را که معلم بعداً از طریق برنامه ذخیره کرده برنمی‌گرداند؛ برای آن، پشتیبان/تاریخچهٔ داده لازم است. rollback مخرب خودکار ارائه نشده است.

## تست‌های اجراشده در زمان ساخت بسته

- ۱۰۲ اجرای تست SQL: همان مجموعهٔ ۵۱تایی، یک بار از پایهٔ اصلی و یک بار پس از نصب SQL ارسالی V335.36؛ با بدنهٔ واقعی PL/pgSQL و PostgreSQL/WASM، داده و auth/attempt_state ساختگی؛ شامل اجرای دوبارهٔ مهاجرت، توقف روی تابع ناشناخته، عدم تغییر دادهٔ تاریخی، حفظ منفی و آزمون چندمرحله‌ای نهایی‌سازی.
- ۳۶ بررسی Node: منطق سایت، عبارت واقعی ذخیره، ورودی فارسی، حدود نمره، null/NaN/Infinity و بررسی نحوی ۱۱ فایل JavaScript.
- ۱۹ تست JUnit واقعی (۱۵ تست جدید سیاست و ۴ تست پیک تصادفی) برای `GradingScorePolicy`، کامپایل با Kotlin 2.0.21 و `-Werror`؛ این اجرای محدود با اجرای کامل Android/Compose یا `testDebugUnitTest` کل پروژه یکسان نیست.
- نصاب جداگانه با پوشهٔ اصلیِ عمداً dirty، فایل stage‌شده، تغییرهای ذخیره‌نشده و تصاویر untracked روی ریموت bare محلی آزموده می‌شود. نتیجه و تعداد سناریوها در شواهد تحویل ثبت می‌شود؛ هیچ push به مخزن واقعی انجام نشده و پاسخ API مربوط به CI در آزمایش گیت‌ها ساختگی است.
- verify و preflight، نحو Kotlin/JS و کنترل grants اجرا شده‌اند. unresolvedهای پین‌های قدیمی به معنی اجرای همهٔ JUnitها نیستند.

بیلد کامل اندروید، کل JUnitهای پروژه، RLS/JWT واقعی، چاپ PDF و آزمون واقعی production در محیط ساخت بسته اجرا نشده‌اند. آن‌ها بخشی از گیت CI و چک‌لیست staging پیش از main هستند.
