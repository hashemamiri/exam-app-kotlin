# V342 — پنجرهٔ ۹۰ ثانیه‌ای سفارش پرداخت کیف پول

## چه چیزی عوض شد؟

پیش‌تر اگر یک سفارش پرداخت نیمه‌کاره می‌ماند (مثلاً وسط پرداخت اینترنت قطع می‌شد یا
صفحهٔ بانک بسته می‌شد)، مدیر یا معلم تا **۳ دقیقه** (در بعضی نسخه‌ها ۳۰ دقیقه) نمی‌توانست
سفارش تازه بسازد و فقط این پیام را می‌دید:

> یک سفارش پرداخت باز دارید؛ ابتدا همان را تکمیل یا لغو کنید

از V342:

1. سفارش باز پس از **۹۰ ثانیه** خودکار آزاد می‌شود و می‌توان سفارش تازه ساخت.
2. تا آن زمان، پیام دقیقاً می‌گوید چند ثانیه مانده است:

> یک سفارش پرداخت باز دارید؛ ابتدا همان را تکمیل یا لغو کنید یا ۹۰ ثانیه صبر کنید

و مثلاً اگر ۴۰ ثانیه گذشته باشد:

> یک سفارش پرداخت باز دارید؛ ابتدا همان را تکمیل یا لغو کنید یا ۵۰ ثانیه صبر کنید

رقم‌ها فارسی‌اند و هر بار که دکمهٔ «ساخت سفارش پرداخت» زده شود، عددِ تازه محاسبه می‌شود.
این رفتار برای **مدیر و معلم**، در **همهٔ درگاه‌ها** (زرین‌پال، زیبال، آیدی‌پی، سندباکس)
یکسان است.

## نکتهٔ مهم: پولِ پرداختِ دیرهنگام گم نمی‌شود

کوتاه‌کردن پنجره یک خطر دارد که در همین نسخه بسته شده است: کاربر روی سفارشِ قدیمی به
بانک می‌رود، کمی بعد پرداخت می‌کند، ولی آن سفارش دیگر «منقضی» شده است. اگر واریز فقط
سفارش‌های باز را می‌پذیرفت، پول از حساب کاربر کم می‌شد ولی کیف پول شارژ نمی‌شد.

بنابراین در V342 تابع واریز، سفارش‌هایی را که **فقط به‌دلیل گذشت زمان** منقضی شده‌اند
(`error_code = 'expired_open_order'`) هم می‌پذیرد و مبلغ را واریز می‌کند.

سفارش‌هایی که کاربر خودش **لغو** کرده یا درگاه واقعاً **خطا** داده است، همچنان واریز
نمی‌شوند؛ آن‌ها باید از مسیر پشتیبانی بررسی شوند. واریزِ تکراری با یک شمارهٔ پیگیری هم
همچنان بی‌اثر است و موجودی دوبار شارژ نمی‌شود.

## چه چیزی عوض نشده است

- سقف و کف مبلغ شارژ (۱۰۰۰ تا ۱۰٬۰۰٬۰ تومان، مضرب ۱۰٬۰۰۰)
- سقف موجودی کیف پول (۱۰٬۰۰۰۰۰ تومان)
- فهرست درگاه‌ها، رسید پرداخت، گزارش تراکنش‌ها
- دسترسی اجرا فقط برای `service_role` (کلید سرویس هرگز در اپ یا سایت نیست)
- **هیچ تغییری در اپ اندروید و سایت لازم نیست**؛ همین پیام از سرور می‌آید و همان‌طور
  نمایش داده می‌شود. به همین دلیل این نسخه شمارهٔ اپ را بالا نمی‌برد.

## چطور روی سرور اعمال کنم؟

۱. وارد پنل Supabase پروژه شوید: <https://supabase.com/dashboard/project/eazwuyrymsvdkwckdpco>
۲. از منوی چپ **SQL Editor** را باز کنید و **New query** بزنید.
۳. تمام محتوای این فایل را کپی و در آن‌جا Paste کنید:

```
supabase/migrations/20261106_wallet_order_window_90s_v342.sql
```

۴. **Run** را بزنید. باید پیام موفقیت ببینید (چیزی مثل `Success. No rows returned`).

این فایل دو تابع را بازسازی می‌کند و اجرای دوبارهٔ آن اشکالی ندارد.

### بررسی این‌که درست اعمال شده

در همان SQL Editor این را اجرا کنید:

```sql
select
  pg_get_functiondef('public.native_create_wallet_payment_order(uuid,bigint,text)'::regprocedure) like '%90 seconds%'      as window_90s,
  pg_get_functiondef('public.native_create_wallet_payment_order(uuid,bigint,text)'::regprocedure) like '%wait_seconds%'     as countdown,
  pg_get_functiondef('public.native_credit_wallet_payment(bigint,text)'::regprocedure)          like '%expired_open_order%' as late_credit;
```

هر سه ستون باید `true` باشند.

## آزمون‌هایی که انجام شد

روی یک PostgreSQL ۱۷ واقعی، جدول‌های کیف پول از خود مهاجرت‌های پروژه ساخته شد و
سناریوها اجرا شد (زمان با عقب‌بردن `created_at` شبیه‌سازی شد):

| سناریو | نتیجه |
|---|---|
| ساخت سفارش برای معلم و مدیر | قبول |
| ساخت سفارش برای دانش‌آموز | رد با «حساب کادر مدرسه معتبر نیست» |
| تلاش دوباره بلافاصله | پیام «… یا ۹۰ ثانیه صبر کنید» |
| تلاش دوباره پس از ۴۰ ثانیه | پیام «… یا ۵۰ ثانیه صبر کنید» |
| تلاش دوباره پس از ۸۹ ثانیه | پیام «… یا ۱ ثانیه صبر کنید» |
| تلاش پس از ۹۱ ثانیه | سفارش تازه ساخته می‌شود |
| پرداخت موفق روی سفارش منقضی‌شده | موجودی شارژ می‌شود، وضعیت `paid` |
| واریز دوباره با همان شمارهٔ پیگیری | بی‌اثر، موجودی دوبار شارژ نمی‌شود |
| سفارش لغوشده / خطای واقعی درگاه | واریز نمی‌شود |
| مبلغ نامعتبر، درگاه نامعتبر، سقف موجودی | همچنان رد می‌شوند |

هر سه فایل SQL (مهاجرت V342 و دو فایل دستی `sql/manual/SQL_WALLET_*.sql`) جداگانه
آزموده شدند و رفتار یکسان دادند؛ پس اگر بعداً آن فایل‌های دستی دوباره اجرا شوند،
این اصلاح پس‌رفت نمی‌کند.

نگهبان `scripts/check_wallet_roles.py` هم گسترش یافت و در `preflight` اجرا می‌شود:
اگر روزی پنجره از ۹۰ ثانیه برگردد، شمارش معکوس حذف شود، رقم‌ها لاتین شوند یا مسیر
واریز دیرهنگام بسته شود، بررسی شکست می‌خورد. این نگهبان با ۷ سناریوی خرابکاری
عمدی آزموده شد و همه را گرفت.
