V38 صریحاً پرداخت بانکی را برای مدیر باز کرده بود (متن خطا هم «حساب کادر مدرسه معتبر نیست» بود).
V335.32 برای افزودن درگاه **زیبال** همان تابع را از روی الگوی قدیمیِ «فقط معلم» بازسازی کرد؛
در نتیجه نقش `manager` بی‌صدا حذف شد و مدیر پیام «حساب معلم معتبر نیست» می‌گرفت.

بررسی کل مسیر پرداخت نشان داد **فقط همین یک تابع** محدودیت نقش دارد:

- `native_credit_wallet_payment` (واریز پس از تأیید) — بدون محدودیت نقش
- `native_set_wallet_payment_authority` — بدون محدودیت نقش
- `native_fail_wallet_payment_order` — بدون محدودیت نقش
- `native_wallet_snapshot` (نمایش موجودی) — بدون محدودیت نقش
- Edge Function `wallet-payment` — بدون بررسی نقش (به تابع SQL تکیه می‌کند)

پس اپ و سایت مقصر نبودند و نیازی به تغییر کد اپ یا سایت نیست.

## اصلاح

مهاجرت تازه: `supabase/migrations/20261106_wallet_manager_role_v341.sql`

اختلاف تابع تازه با تابعِ در حال کار روی سرور **فقط دو خط کاری** است:

```diff
-        select 1 from public.profiles where id = p_user and role = 'teacher'
-    ) then return jsonb_build_object('error', 'حساب معلم معتبر نیست'); end if;
+        select 1 from public.profiles where id = p_user and role in ('teacher', 'manager')
+    ) then return jsonb_build_object('error', 'حساب کادر مدرسه معتبر نیست'); end if;
```

همهٔ محافظ‌های V335.32 دست‌نخورده مانده‌اند: درگاه `zibal`، انقضای سفارش نیمه‌کاره پس از
۳۰ دقیقه، یکتا بودن سفارش باز، سقف موجودی ۱۰٬۰۰۰٬۰ تومان، بازهٔ مبلغ شارژ،
`security definer` با `search_path` ثابت و `grant execute` فقط به `service_role`.

**اجرا:** Supabase → SQL Editor → کل فایل، یک‌بار. تکرارش بی‌خطر است و داده‌ای تغییر نمی‌کند.
چون پایگاه‌داده مشترک است، اپ و سایت هر دو بلافاصله درست می‌شوند.

## نکتهٔ topology (مهم برای نسخهٔ بعدی)

این بسته روی **main** نشست در حالی که V340 هنوز روی **staging** تأیید نشده بود. اگر نصاب
می‌خواست staging را ساده fast-forward کند، push رد می‌شد و `promote.py` بعدی هم می‌شکست.
پس الگوی نصاب اصلاح شد: در حالت `TARGET = main`، اگر staging جلوتر باشد، نصاب main را
**داخل staging ادغام می‌کند** و هر دو شاخه اصلاح را می‌گیرند؛ در نتیجه main نیای staging
می‌ماند و مسیر promote باز است.

برای اینکه این ادغام بدون تعارض بماند:
- گزارش V341 در همین فایل جدا نوشته شد (نه انتهای `HANDOFF_KOTLIN_MIGRATION_FA.md`) چون آن
  فایل روی staging بخش‌های V340 را دارد.
- گام `wallet_roles` در `preflight.py` عمداً کنار `verify_native_final` گذاشته شد، نه چسبیده
  به گام `kotlin_visibility` که فقط روی staging بود؛ این دو تغییر در دو ناحیهٔ جدا هستند.
- `scripts/check_kotlin_visibility.py` هم در بسته هست تا `preflight` روی main هم سالم بماند
  (روی درخت V339.2 آزموده شد: ۲۷۷ فایل، PASS).

## V341.1 — چرا شمارهٔ نسخه به `1.03.60` رفت و مسیرهای CI اصلاح شد

**خطای CI پس از نشستن V341 روی main:**

```

شماره را در text/APP_VERSION.txt یکی زیاد کنید.
```

**علت:** V340 با شمارهٔ `1.03.59` روی main منتشر شده بود. بستهٔ V341 هیچ فایل اپی را تغییر
نمی‌داد، پس شماره همان `1.03.59` ماند؛ اما CI اپ اجرا شد و گام «هر نسخه فقط یک‌بار منتشر
می‌شود» (`android.yml`) آن را رد کرد.

**چرا CI اپ اصلاً اجرا شد؟** فهرست `paths` در `android.yml` این‌ها را مستثنا می‌کرد:
`site/**`, `docs/**`, `text/CHANGELOG_FA.txt`, `text/*.md`, `relay/**`, `supabase/**`.
ولی **`scripts/**` و `sql/**` مستثنا نبودند** و بستهٔ V341 نگهبان‌های `scripts/` و
فایل‌های `sql/manual/` را داشت.

**اصلاح (به انتخاب کاربر):**

1. `text/APP_VERSION.txt` → `1.03.60` و یادداشت بازار V341 (رفع خطای شارژ کیف پول مدیر).
   این تنها راه سبز شدن همان اجرای CI است، چون قاعدهٔ تکراری‌نبودن شماره قابل دور زدن نیست.
2. به `paths` در `android.yml` دو خط `- '!scripts/**'` و `- '!sql/**'` اضافه شد تا اصلاحات
   زیرساختیِ آینده (نگهبان‌ها، SQL دستی) مثل `site/` و `supabase/` دیگر APK اجباری نسازند.
   توجه: اگر کامیتی هم‌زمان کد اپ را هم تغییر دهد، CI مثل قبل اجرا می‌شود.
3. `push_checked` در قالب نصاب تعمیم یافت: پیش‌تر فقط `site.yml` را می‌شناخت، پس اگر توکن
   گیت `scope=workflow` نداشت، تغییر `android.yml` باعث توقف کل نصب می‌شد. حالا **هر** فایل
   workflow تغییریافته در کامیت شناسایی، کنار نصاب با پسوند `.pending` ذخیره و از کامیت
   برداشته می‌شود تا بقیهٔ نسخه اعمال شود؛ سپس می‌توان آن را دستی در GitHub جای‌گذاری کرد.

**اگر توکن شما `scope=workflow` ندارد:** نصاب خودش نسخهٔ تازهٔ `android.yml` را کنار
خودش ذخیره می‌کند و بقیهٔ بسته (شمارهٔ نسخه + یادداشت) را اعمال می‌کند؛ در آن حالت CI سبز
می‌شود ولی بند ۲ اعمال نشده و باید دستی از GitHub → `.github/workflows/android.yml` → Edit
محتوای فایل `.pending` را جای‌گذاری کنید.
